## Context

Step 1 of RFC-0018 refused `upload: true` at load, the visible form of the Rust port's deferral of multipart upload:
the engines stream each file into an object stream and hand the function stream routes, and the packs have no such
primitive. Eric chose the bounded form proposed in the answer to his question, with the LLM helper's intake as its
first use: RFC-0016's `attachments` read files from `llm.attachments.root`, and until now something outside the
helper had to put them there.

## What was done

- **`rest_routing.py`:** `upload` is a field of an entry; the refusal is gone.
- **`async_http_request.py`:** the engines' upload keys - `filename`, `file_type`, `file_length` as parallel lists,
  the `upload` tags, `size` - plus the pack key `contents` holding each file's bytes in place of the stream routes;
  `UploadedFile` (name, content type, size, tag, bytes), `files()`, `is_file`, `content_length`, `add_file`. Both
  classes exported.
- **`rest_automation.py`:** on a POST entry with `upload: true` and a `multipart/form-data` body the edge reads the
  parts with aiohttp's multipart reader instead of buffering the body: a part with a filename is a file (its field
  name the tag, its declared type or octet-stream), any other part a text field that becomes a query parameter; the
  files together may not exceed `rest.upload.max.bytes` (16 MiB) - a 413 the moment they do, before anything is
  delivered; a malformed body is a 400; the request body stays absent (Java parity). A non-multipart body on such an
  entry, and a multipart body on an entry without the flag, dispatch as before. A refusal while preparing the request
  is answered without a trace record.
- **The LLM helper:** `llm.upload` behind `POST /api/llm/upload` (`resources/rest.yaml`, `rest.automation: true` in
  its `application.yml`): each file saved under `uploads/` inside the attachments root under `<id>-<the original name
  made safe>` (opened exclusively, never an overwrite; hidden-entry dots stripped, since the attachments rules refuse
  them), in a worker thread; the reply lists the references - `path` inside the root, `filename`, `media_type` by
  the first bytes else the declared type, `bytes`, `sha256` (the hash the audit keeps) and `attachable` (a PDF or an
  image the model takes as it is, else a conversion first). No file is a 400 by name; no root a 503 by name. The log
  carries the count and the bytes, never a name or content.
- **Proof:** the vector file at version 2 (129 cases: an upload entry accepted, the request map with the upload keys
  and `contents_base64` as the carrier of bytes in JSON, `upload_read_cases` over the accessors);
  50 tests in `tests/test_rest_automation.py` (four new over HTTP: the files and the field delivered, a JSON
  post on an upload entry, multipart on an entry without the flag, the 413) and `tests/test_llm_upload.py` (three:
  the saved files and references, the 400 and the 503, the safe names).
- **Docs:** README (the upload sentence of the REST section), the helper README ("Uploading documents"), the
  helper's `application.yml` and `rest.yaml`, CHANGELOG Unreleased Added 14.

## Decisions

- **Eric's:** the upload feature after the step-1 PR, with the helper's document intake as the use case.
- **Made here, as defaults without a ruling (listed on the thread):** one bound for all the files of an upload; the
  body absent and the bytes in `contents`; multipart without the flag stays bytes; the intake's naming; `attachable`
  by the first bytes; the helper turns REST automation on in its own configuration.
