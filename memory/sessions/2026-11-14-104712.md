**Title:** The MCP binding's bound routes become aliases of one `@preload` function, `mcp.tool`

## Context

Follows 2026-11-14-073523. After the engine-side drive of the diagram assistant (mercury-composable #626 and #627), Eric
asked which function of this pack serves `diagram.render.mcp`. The answer was a closure: `_handler(server, binding)`
returned an inner `call` that `Binding.boot` registered with `default_registry.register`, one closure per allowlisted
tool. Eric asked for the composable shape instead: the function exposed with the `@preload` decorator, as `llm.chat` and
`mcp.health` are.

## The design question, and Eric's ruling

A `@preload` route is a literal at import time, while the binding's routes come from the servers file at boot, so one
declared function has to serve every bound route and learn which one it was called as. The pack's host strips `my_*`
headers at ingress and adds only `my_correlation_id`, so the engines' `my_route` header is not available to a function;
but the bus sets a `TraceInfo` whose `route` is the executing service's route for every execution, and `get_trace()` is
public - the pack's counterpart of the engines' `PostOffice.getRoute()`. No SDK change was needed.

Eric then suggested a generic MCP client: one fixed route, the destination server encoded in the call, reusable for any
server. ADR-0033 (accepted the same day in mercury-composable) lists that shape as rejected alternative (c): a target hidden
in the call is one the catalog cannot certify. The certifiable form would be an optional `headers` map on the catalog row,
sent by the loop with each call - an engine change in both engines, with the shared vectors, both packs, the example and
the ADR amended. Offered the three shapes, Eric chose to keep one route per allowlisted tool and refactor the shape only.

## What changed (branch `refactor/mcp-binding-preload`, PR #52)

- `extensions/mcp-binding/mcp_binding.py`: `mcp_tool` is declared with `@preload(route="mcp.tool", instances=10,
  private=True)`; it reads `get_trace().route`, resolves the server and the allowlisted tool through `Binding.bound(route)`
  (404 for a route bound to none, `mcp.tool` itself included), checks that the body is a map (400) and calls the tool.
  `Binding.boot` fills `routes` (route to server and tool) and registers each allowlisted tool's route as an alias of
  `mcp_tool` with the server's `instances`; `shutdown` clears both tables. The `_handler` factory is gone.
- `tests/test_mcp_binding.py`: the calls go through `PostOffice` local RPC, the path behind the HTTP host, so the alias
  dispatch and the route in the execution context are what the tests exercise; the `po` fixture closes the registry's bus
  after each test (its workers bind to the loop of their first use); the `servers` fixture installs the fresh `Binding`
  as the module's instance, the one `mcp_tool` and `mcp_health` read; the first test pins the shape: every bound route's
  handler is `mcp_tool`, public, with the server's `instances` (3), `mcp.tool` private, a call to it a 404.
- `extensions/mcp-binding/README.md` and the CHANGELOG's Unreleased entry describe the shape.
