## Ratified rationale (now in README + registry.py docstring)

Python is the only wrapper runtime with TWO library ecosystems: the synchronous world
(`requests`, NumPy/pandas and most ML inference stacks, database drivers) and asyncio.
Plain `def` handlers run in the executor so blocking work never stalls the event loop
that hosts every other function — the Python analog of the Java engine's virtual
threads ("write sequential blocking-style code; the platform makes it safe"). `async
def` serves asyncio-native I/O and composition. Java needs one style (virtual threads
make blocking free); node needs one style (ecosystem uniformly non-blocking); python
needs both. Detection stays automatic (`inspect.iscoroutinefunction`).

## The sync bridge (the composition gap, closed)

Previously a sync handler could not call siblings (PostOffice.request is a coroutine;
executor threads have no loop). Now:

- `bus._execute` stamps the host loop into a `_HOST_LOOP` contextvar just before
  `copy_context()`, so the executor thread carries loop + trace.
- `PostOffice.request_sync()/send_sync()` submit the same coroutines onto the host loop
  via `run_coroutine_threadsafe`, blocking only the worker thread. **Key subtlety:
  contextvars do NOT travel through run_coroutine_threadsafe** — the bridge captures
  `get_trace()` on the executor thread and re-establishes the SAME TraceInfo object
  inside the submitted task, so the trace chain is unbroken (pinned).
- Guards teach: called on the event loop → RuntimeError "await request()/send()
  instead"; called off-host → RuntimeError pointing at `asyncio.run(po.request(...))`.
- Inner deadlines still shape 408/404 envelopes; an outer `future.result` margin
  (ttl + 10s) guards a wedged path so an executor thread can never hang forever.
