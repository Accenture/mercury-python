- **Defect found here and fixed:** the inbox's decision write was unconditional. Two devices deciding one card at the
  same moment both pass the open check and both reach the engine, which resumes at most once; the loser gets
  `nothing waiting`, and the row took whichever outcome landed last - in the drive the 410 landed first (22 ms against
  1.5 s), so the row happened to end right, but the opposite order would have overwritten the accepted decision and its
  operator. Now `MemoryInbox.decided` and `SQL_DECIDED` apply a write only when the row is still open or the state is
  `answered` (an acceptance always wins); `PostgresInbox.decided` answers with the row as stored when the guard kept
  it; the handler returns that row with the invoker's own outcome and broadcasts nothing for it. Re-driven twice live:
  the losing device's 410 turned the row expired for a moment, the acceptance won it back.
- **Shared vectors version 2** (`tests/vectors/agent-question-vectors.json`, 31 cases): the two-devices transition case
  pins both the overwrite that must not happen and the sequence standing still; the description says why. A race test
  with a scripted reply endpoint (`t-race-slow`, `t-race-fast`) pins both orderings through the handler.
- **Narrowed a claim** in the ask-person README: who decided reaches the audit store only when the note reaches the model
  (a refused call); an approved call's decision stays on the channel's record and in the log - a drive finding, with the
  loop's follow-up recorded in the RFC.
