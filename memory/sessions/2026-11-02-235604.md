**Branch `feat/llm-chat-loop-contract`, commit `db6a5f1` (stacked on `5fddcdc`):**

- A request with `tools` is a loop turn (`_loop_turn`); without it `llm.chat` is unchanged. Request: `tools`
  (`name` per `^[a-zA-Z0-9_-]{1,128}$`, unique; `description`; `input_schema`; `strict`; any other key a 400, so a
  catalog's `route` or `approval` never reaches the model), `conversation` (32 hex), `turn`, `results`
  (`{id, output}` or `{id, error}`), `ttl` and `retention` (seconds or `30m`/`12h`/`2d`; defaults
  `llm.transcript.ttl` 7d and `llm.transcript.retention` 0). The loop fields without `tools` are a 400 on `llm.chat`,
  and any of them on `llm.stream` is a 400.
- Reply: `status` (`done`/`tool_use`/`refusal`/`cap`), `text`/`data`, `calls [{id, name, input}]`,
  `refusal {category}`, `cap` (`max_tokens`/`context`, an addition to spec section 3.2 so the loop can name the cap),
  `conversation`, `turn`, `model`, `stop_reason`, four-field `usage`, `request_id`. A cut-off turn returns no calls.
  An end with nothing usable stays the 422; `pause_turn` and a `tool_use` stop with no call are 502s.
- The record: model (pinned at the first turn; another `params.model` is a 400), messages in the provider's format,
  turn count, the last turn's call ids, closed. Each block is stored as `to_dict(mode="json")`, which is how the SDK
  serializes a returned block it is handed back (`openapi_model_dump`: `exclude_unset`), so thinking signatures replay
  unchanged. Results become one `tool_result` message in call order, non-text as compact JSON (the Node twin's
  `JSON.stringify`). Checks: 404 not found or expired, 409 closed, 409 stale turn, 400 for missing, unknown or
  duplicate result ids. Each write is a compare-and-set on the turn (409 when lost: a duplicated turn never forks).
- Stores (`llm.transcript.store`, required for a loop turn - a `503 transcript store not configured` - and set to
  `memory` in the sample config): `MemoryStore` (one process) and `RedisStore` (the new `redis` extra; one hash
  `transcript:{conversation}` with `turn` and `record`; a single-key Lua script for the compare-and-set, safe on a
  cluster; connection from `llm.transcript.redis.{host,port,username,password,ssl,database,timeout.ms}`, the engines'
  `redis.*` suffixes; standalone client only). Every write sets `ttl`; a run the model ends (done, refusal, context)
  takes `retention`, 0 deleting it; a run cut off at `max_tokens` keeps `ttl`. A store failure is a 503 by name.
- Decisions (mine, stated in the checkpoint, for Eric's review): **no server-side fallbacks on a loop turn** (the
  claude-api reference: a fallback moves the conversation to another model, sticky for about an hour, and a mid-output
  fallback requires omitting blocks on replay - both break the pinned, append-only record; the graph routes
  `status: refusal`); **caching** by a marker on the system block plus top-level automatic caching, never a marker on
  a stored block; **no `eager_input_streaming`** (the helper reads only the final message, and the buffered default
  keeps the API's input validation).
- `llm.health` info reports `transcript_store`; trace annotations add `llm_status`, `llm_turn` and the cache tokens;
  the log line carries status, turn and usage, never content or the conversation reference.
- Shared vectors: `tests/vectors/llm-loop-vectors.json`, contract `llm-chat-loop` v1, 66 cases (34 request checks, 32
  runs of one to three turns), digest `8b664486...` pinned in the test. Written by a generator in the session
  scratchpad that states each expectation from the contract, never from the helper; lines stay compact (a map or list
  that fits in 100 columns stays on one line; 6296 lines).
- Docs: the README's "The loop contract" and "The transcript store", configuration rows, the Redis run, the Bedrock
