## What We Did

- **Why.** Building the transcript audit store (#59) showed that `AppConfig.get` returned a `-D` override as written, so
  `-Dkey='${POSTGRES_PASSWORD}'` would have sent the literal text; the helper's yml took the credential from the
  environment instead. Eric asked whether to support substitution in a `-D` value; recommended as a parity change in all
  four runtimes (the Java engine returned a system property raw too), and he asked for it after the Node lockstep.
- **The change.** `src/mercury_composable/config.py`: an override's string value (a `-D` argument, or `AppConfig.set`)
  goes through `_substitute` like a file value - an environment variable with a default, or a reference to another
  configuration key, resolved at read time; a non-string override is returned as it is. `tests/test_config.py`
  `test_an_override_value_resolves_references_like_a_file_value` (a reference to a file key inside a URL, a default, an
  unresolved reference as None, the environment read at read time, a `set()` value). Gates: ruff clean, basedpyright 0
  errors, pytest 439 passed, 65 skipped.
- **Record.** README (the configuration paragraph), CHANGELOG Unreleased Changed 1 (after Added, the Keep a Changelog
  order). In lockstep with the Node pack; the engines' twins are mercury-composable `feat/system-property-substitution`
  and mercury Increment 203. The helper READMEs' caveat ("a -D value is taken as written") can go once the PRs merge.

## Decisions

- A runtime override's value is resolved like a file value (Eric, 2026-11-17); the one compatibility edge, a `-D` value
  that relied on a literal `${...}`, is accepted - a file value never allowed it.
