## Context

The field runs many utility scripts in Python and Node that are not standard anything - each its own web framework,
its own error shape, its own headers and deployment. The engines answer the same need with REST automation: a
`rest.yaml` that *is* the router ("config is the code"), mapping a URL and its methods to a composable function, with
CORS, header transforms, an authentication function, a timeout, tracing and static content. The question is whether
the packs can carry the same feature, so a field utility app in Python or Node is designed and deployed like an engine
application. This session read the engines, the packs' hosts and the packs' history; it wrote no code. A decision at
the Vision altitude is the maintainer's; this log is the evidence for it.

## What REST automation is in the engines (read 2026-11-24)

- **Java** (`system/platform-core`, package `org.platformlambda.automation`): `RoutingEntry` (the parser, 1007
  lines), `HttpRouter` (the request path, 1291), `HttpRequestHandler` (the vert.x handler, 101), `AsyncHttpRequest`
  (the request model, 878), `AsyncHttpResponse` and `EventStreamRenderer` (the reply and the stream), `SimpleHttpUtility`
  (the error shape), the static-content filter, `CustomContentTypeResolver` and `MimeTypeResolver`. The grammar is
  documented twice: `docs/guides/rest-automation/rest-grammar.md` (rule-based) and `rest-automation.json` (machine
  readable, 16 entry fields, 6 invariants; a CI drift test keeps it in step with `RoutingEntry.VALID_METHODS`), with
  `ai-agent-guide.md` for an agent authoring a file and a guide fixture `rest-bindings.yaml` loaded through the
  production parser.
- **Rust** (`crates/platform-core/src/automation/`): `routing.rs` (856), `server.rs` (2242, hyper), `event_api.rs`
  (718), `http_client.rs` (1721), with `tests/rest_automation.rs` (1565 lines, 33 named cases) and
  `tests/static_content.rs`. The port is explicit about what it left out: the HTTP relay (`http(s)://` service,
  `url_rewrite`, `trust_all_cert`) is refused at load as "not yet ported", the A/B dual service fails to load,
  multipart `upload` is deferred, the authentication routing specs (`'header: value: svc'`) are not ported, one
  `yaml.rest.automation` location only, XML passes as text, `custom.content.types` and `mime.types` are not read,
  `static.html.folder` is fixed to `resources/public`. An entry whose service is not registered at start is skipped
  with a warning. Everything else is Java parity, test-pinned: the request-model keys, the content-type dispatch
  table, content negotiation from `Accept`, the error body `{status, message, type: "error"}`, 404/405/401/408,
  CORS preflight 204, header transforms in keep-drop-add order, the most-specific route winning, `x-ttl` overriding
  the entry's timeout, the correlation id always ensured and echoed, `traceparent` winning over the trace-id header,
  per-endpoint header-name overrides, `stream: true` on a dedicated ordered lane.
- **Default entries** (both engines): `POST /api/event` and the four actuators are rest.yaml entries merged when a
  file does not claim their URLs, so a user entry can attach `authentication`, CORS or another timeout to
  `/api/event` (the lambda-example's `event.api.auth`).

## What the packs already have (the primitives the port would sit on)

Both hosts, in lockstep: one HTTP server on `rest.server.port` (aiohttp in Python; `node:http` hand-rolled in Node,
two runtime dependencies each); `POST /api/event` with the engines' ttl, async and reserved-header semantics; the
actuators; static content from `resources/public` under `static.html.folder` (#73 / mercury-nodejs #138, which
withdrew the 2026-08-24 note that the wrappers serve no static files); `Platform.add_routes` for an extension's own
pages and streams; the bus with per-call ttl and `DeliveryTimeout`, workers per route and the trace records a Java
callee leaves (the edge's `http.request` record is already the forwarder's SERVER kind); the streaming sink and the
SSE helpers (`event_stream.py` / `event-stream.ts`); `AppException` as the portable error; a returned `EventEnvelope`
kept as the reply with its status and headers; `${ENV:default}` and `-D` configuration under the resources rule.
REST automation is a routing table and a request model in front of the same bus - nothing it needs is missing from
the host, and nothing in it is orchestration.

## Prior art

- **The legacy Node pack carried a full REST automation port** before the August 2026 repurposing (tags v4.2.40 to
  v4.3.28): `src/system/rest-automation.ts` (937 lines), `src/util/routing.ts` (the parser, 822),
  `src/models/async-http-request.ts` (866), `src/services/async-http-client.ts` (407), the default `rest.yaml` with the
  five system entries, a guide chapter. It ran on Express with body-parser, cookie-parser and busboy (upload), kept
  an HTTP context per request answered by an `async.http.response` function, and declared its variation from Java
  (the body-parser order, a 2 MB raw limit). It is a reference for the TypeScript parser and the request model; its
  Express base is not a fit for the current host, which is hand-rolled on `node:http` with two dependencies.
- **The legacy Python pack never had one** (no `rest` file in its history); it relied on the Java engine's REST
  automation through the language connection.
- **The polyglot design of 2026-08-22** (mercury-composable `draft-design-specs/polyglot-script-runner.md`, D0-D8)
  started from the field's scripts as child processes and pivoted to long-lived Event-over-HTTP peers. REST
  automation on the packs is the next step on the same line: the peer becomes the engines' HTTP application host.

## Internal demand, already visible

The packs' own extensions mount HTTP routes by hand today: the agent-question app six routes (`/questions/config`,
`/questions/events`, `/questions`, `/transcripts`, `/transcripts/{conversation}`, `POST /questions/{id}/decide`) and
the ask-person main flow four (`/ask/config`, `POST /ask/reply`, `/ask/{ticket}/wait`, `/ask/{ticket}`), in both
packs, each with its own method and path checks, its own bearer or OAuth check and its own error rendering. All but
the SSE feed and the OAuth shell are what a rest.yaml entry plus a `@preload` function would express, with
`authentication` as a function and the error shape for free.

## Assessment

**Viable, with no new dependency in either pack, and the natural next step of the polyglot initiative. The scope fence
holds: REST automation is ingress configuration, not orchestration - no flow, no graph, no persistence, no pub/sub
enters the package. What changes is the Vision's wording: "a deliberately tiny Event-over-HTTP wrapper" becomes the
engines' HTTP application host for functions written in Python or Node. That amendment, and the opening of a
`(blueprint)` gap, are the maintainer's gates; nothing was opened here.**

### The shape proposed for the RFC

- **Switch and file.** `rest.automation: true` (off by default, so every installation today is unchanged);
  `yaml.rest.automation`, one location, default `classpath:/rest.yaml` read as `resources/rest.yaml` next to the
  application file under the resources rule, `file:` for an absolute path - as `static.html.folder` is read.
- **One server, one port.** The host's paths become the default entries, as in the engines: `POST /api/event` and the
  actuators merged when the file does not claim them, so a user entry can attach `authentication`, CORS or a timeout
  to `/api/event`. Order of precedence: rest.yaml entries (the defaults among them), then an extension's mounted
  routes, then static content, then the engines' error shape.
- **Version 1 = the Rust port's subset** (Java parity where the Rust port has it): function binding; `{param}` and a
  trailing `*`; most-specific match; `timeout` clamped 1 s to 5 min with `x-ttl` winning; `cors` with the preflight
  204; `headers` keep-drop-add; `authentication` in the simple form, the verdict's headers as the `session` map;
  `tracing` with `traceparent` first, then the trace-id header, then a fresh id, the correlation id always ensured
  and echoed, the three per-endpoint header-name overrides; `stream: true` rendered as plain SSE or chunked text on
  the existing sink; the content-type dispatch table and the `Accept` negotiation; the error body and statuses;
  `static-content.no-cache-pages` and `filter` (a function on the filter route - the packs skipped both with #73
  because they presupposed the parser); the `AsyncHttpRequest` map with the engines' keys; a function returning an
  envelope sets the status and headers. The edge records `http.request` with path `GET /api/x` as the engines do,
  so the forwarder's kind rule already makes it the SERVER span.
- **Refused by name in a pack**, so the grammar itself shows the scope fence: `flow` and `service: http.flow.adapter`
  (there are no flows here - the message says where they live), the HTTP relay, the A/B dual service. **Deferred** as
  in the Rust port: `upload` (aiohttp has multipart; Node would need a small parser or busboy), `custom.content.types`,
  `mime.types`, XML. **Out of scope:** the outbound `async.http.request` client (Python has aiohttp, Node has `fetch`)
  and WebSocket.
- **Proof, the packs' way:** a shared `rest-automation-vectors.json`, byte-identical across the two packs, for the
  pure half - parser validation with the engines' messages, route matching, header transforms, negotiation, the
  request-map shape - plus the engines' `rest-automation.json` grammar loaded as a fixture, and the Rust test list
  as the behavioural checklist (33 cases). A live drive through a browser and through an engine's
  `async.http.request`.
- **Sizing** (each pack; the two in lockstep as every feature so far): the parser about the Rust `routing.rs`, the
  router and edge about a third of the Rust `server.rs` (the host already has the event path, the stream renderer
  and the static file service), the request model small, tests and vectors the larger half of the work - a build
  of the ask-person size, one sprint per pack.

### Open rulings for the maintainer

1. The Vision amendment: the elevator statement and README "Scope" - "the engines' REST automation edge" added to
   "What it should become", the non-goals unchanged.
2. `/api/event` as a default entry (recommended, engine parity): it then carries the engines' default timeout where
   today only `x-ttl` bounds it.
3. `upload` in version 1 or deferred with the Rust port.
4. Whether the packs' own extensions migrate their hand-mounted JSON routes to rest.yaml entries afterwards (a
   follow-up, not part of the port).
